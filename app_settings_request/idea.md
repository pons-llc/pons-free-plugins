# アプリ設定変更依頼プラグイン(app_settings_request)

「このアプリのこのフィールドを必須にしてほしい」「選択肢を増やしてほしい」といったkintoneアプリの設定変更を、
レコードとして**依頼 → 承認**し、プロセス管理で「完了」になった時点でREST APIにより対象アプリへ自動反映
(運用環境へのデプロイまで)するプラグイン。本プラグインを追加したアプリ(以下「依頼アプリ」)の
1レコード = 1件の変更依頼(1フィールドに対する1つの変更)。

## 機能概要

1. **プラグイン設定の保存時**: 依頼アプリに必要なフィールドとスペースを作成し、プロセス管理をONにする
   (プロセス管理を一度も設定していないアプリには既定の承認フローを作成する)。最後に運用環境へ反映する。
2. **レコード追加/編集画面(スペース)**: 対象アプリをアプリ名で検索(またはアプリIDを直接入力)して選び、
   対象アプリのフィールドを「ラベル(フィールドコード)」で選択し、そのフィールドで変更できる内容を選んで
   変更後の値を入力する。保存時に変更内容をJSONとしてレコードに保存する。
3. **レコード詳細画面(スペース)**: 依頼内容(対象アプリ・フィールド・変更内容・変更前→変更後)を表示する。
   承認者はこれを見て承認する(表示はJSONから毎回生成するため、表示内容=反映される内容)。
4. **「完了」ステータスへのアクション実行時**: 実行ユーザーの権限で、対象アプリの管理権限を確認 → 反映
   (`PUT`/`DELETE preview/app/form/fields.json`)→ 運用環境へ反映(デプロイ)まで行い、結果をレコードに記録する。
   失敗した場合はエラーを表示してアクションをキャンセルする(ステータスは「完了」にならない)。

## 変更できる内容(フィールドの設定値の有無から自動判定)

対象アプリの`GET /k/v1/app/form/fields.json`が返すフィールド定義に、そのプロパティが存在する場合のみ選択肢に出す
(「フィールドの設定を変更するAPI」のリクエストパラメーターに対応。kintoneドキュメントMCPで確認済み)。

| 変更内容 | 対象 | 入力 | APIへ送るプロパティ |
| :-- | :-- | :-- | :-- |
| フィールド名(ラベル)の変更 | ステータス/作業者/カテゴリー以外の全フィールド | 文字列 | `label` |
| フィールドコードの変更 | 同上 | 文字列(既存コードとの重複不可) | `code` |
| フィールド名の表示/非表示 | `noLabel`を持つフィールド | 表示する/表示しない | `noLabel` |
| 必須項目にする/しない | `required`を持つフィールド | 必須/任意 | `required` |
| 値の重複を禁止する/しない | `unique`を持つフィールド | 禁止/許可 | `unique` |
| 初期値の変更 | 文字列1行・文字列複数行・数値・リンク(ルックアップ以外)、ラジオボタン・ドロップダウン(選択肢から1つ)、チェックボックス・複数選択(選択肢から複数) | 種類に応じた入力 | `defaultValue` |
| 選択肢の変更 | `options`を持つフィールド | 既存の選択肢ごとに新しい名前・削除、追加、↑↓で並べ替え | `options`(キー=変更前の名前。+初期値の自動補正) |
| 文字数の制限 | `maxLength`を持つフィールド | 最小・最大(空欄=制限なし) | `minLength`/`maxLength` |
| 値の範囲 | `maxValue`を持つフィールド | 最小・最大(空欄=制限なし) | `minValue`/`maxValue` |
| フィールドの削除 | 上記のうちグループ・テーブル・システムフィールド(レコード番号/作成者/更新者/作成日時/更新日時)以外 | なし | `DELETE`(データも削除される旨を警告) |

- テーブル内のフィールドも対象にできる(`{テーブルコード: {type: 'SUBTABLE', fields: {...}}}`で更新、
  `DELETE`は内側のフィールドコードを直接指定。**検証環境で実機確認済み**、2026-10-21)。
- `PUT`は送ったプロパティだけが変わり、送らなかったプロパティ(例: `required`)は保持される(ドキュメントの
  「省略するとfalse」という記載に反し、**実機では保持されることを確認済み**)。そのため変更対象のプロパティだけを送る。
- 選択肢の変更で、現在の初期値が新しい選択肢に無くなる場合は反映時に初期値を補正する
  (名前を変えた選択肢は新しい名前に追従。削除された場合はドロップダウン: 空、ラジオボタン: 先頭の選択肢、
  チェックボックス/複数選択: 残る選択肢のみ)。

### 選択肢の変更の挙動(検証環境で実機確認済み、2026-10-21、アプリ791)

値は変更後の並び順どおりの`[{ from: 変更前の名前(追加は空), label: 変更後の名前 }]`。一覧に無い既存の選択肢は削除。

| 操作 | APIへの送り方 | 既存レコードの値 | 一覧・グラフの絞り込み条件 | グラフの並び(大項目 昇順) |
| :-- | :-- | :-- | :-- | :-- |
| 並べ替え・追加 | キー=名前、indexを並び順に | 変わらない | 変わらない | 新しい選択肢の順(0件の選択肢は出ない) |
| 名前の変更 | キー=**変更前の名前**、`label`=変更後の名前 | **新しい名前に書き換わる** | **新しい名前に書き換わる** | 新しい名前で同じ位置 |
| 削除 | キーごと送らない | **古い値のまま残る** | 古い名前のまま残る(該当し続ける) | 選択肢にない値として末尾 |

- 当初は「1行1選択肢」の入力で名前の変更を「削除+追加」として送っていたが、上記のとおり既存レコードが古い値のまま
  取り残されるため、名前の変更はキーに変更前の名前を指定して送る方式に改めた。
- 追加・名前変更の結果が**別の既存の選択肢の名前**になる指定(入れ替え・統合)は、既存レコードの値が意図せず変わるため認めない。
- kintoneは**過去に削除された選択肢名への名前変更**をエラーにする(`既存の選択肢は、過去に削除された選択肢「B2」と同じ名前にできません。`、
  実機で確認)。一方、過去に削除された名前の選択肢を「追加」することはできた。削除履歴はAPIで取得できないため事前チェックはせず、
  反映時のAPIエラーをそのまま表示してアクションをキャンセルする(削除の警告文で予告する)。
- 日付・時刻・日時の初期値(「レコード登録時の日時」との関係が複雑)、ユーザー/組織/グループ選択の初期値・選択肢、
  計算式、ルックアップ・関連レコード一覧の設定はスコープ外。

## 一覧の作成・修正・削除

「変更の対象」で「一覧」を選ぶと、対象アプリの一覧(表形式)を作成・修正・削除する依頼にできる。

| 変更内容 | 入力 | APIへの送り方 |
| :-- | :-- | :-- |
| 一覧の作成 | 一覧名、一覧画面のURL(任意)、表示するフィールド | 全一覧+新しい一覧(表形式、表示順は末尾) |
| 一覧の修正 | 対象の一覧、一覧名、一覧画面のURL(任意。空なら条件・並び順は変えない) | 全一覧のうち対象(キー=変更前の一覧名)の`name`/`filterCond`/`sort`だけを変更。表示フィールドは変えない |
| 一覧の削除 | 対象の一覧、確認チェック | 対象を除いた全一覧 |

- 「一覧の設定を変更するAPI」(`PUT preview/app/views.json`)は**送らなかった一覧を削除する**仕様のため、反映直前に
  `GET preview/app/views.json`で全一覧を取得し、そのまま送り返したうえで対象だけを変える。GETの結果(`id`・`builtinType`を含む)を
  そのままPUTしても変化しないこと、一覧名を変えても`id`が変わらないこと、存在しないフィールドを使った条件・同じ名前の一覧は
  kintoneがエラーにすることを実機で確認済み(2026-10-21)。対象の一覧は`id`で探す(依頼後に名前が変わっても追える)。
- 「（作業者が自分）」(`builtinType: ASSIGNEE`)、「（すべて）」(APIに現れない)、カスタマイズ形式(変更にkintoneシステム管理権限が必要)は
  修正・削除の対象にしない。
- プロセス管理が無効のアプリでも、フィールド定義にはステータス・作業者が含まれるが、一覧に入れると
  「プロセス管理機能が無効に設定されています」エラーになる(実機で確認)ため、その場合は表示フィールドの候補から除く。

### 一覧画面のURLの変換(実機確認済み)

一覧画面で絞り込み・ソートしたときのURLは、条件をフィールドコードではなく**内部のフィールドID**で持つ
(例: `/k/791/?view=20&q=f13466487 = "15"#sort_0=f13466487&order_0=desc&size=20`)。フィールドIDとコードの対応を返す
公開APIは無いため、貼り付けられたURLを**同一オリジンの非表示iframeで開き、そのページの`kintone.app.getQueryCondition()`/
`kintone.app.getQuery()`(公式のJavaScript API)**でフィールドコードの条件(`amount = "15"`)・並び順(`amount desc`)に変換する
(約0.6秒)。`?query=<フィールドコードのクエリ>`形式のURLも同じ方法で変換できる。
- iframeで開くのは、同じオリジンの`/k/{アプリID}/`(ゲストスペースは`/k/guest/{ID}/{アプリID}/`)のパスで、アプリIDが選択中の対象アプリと
  一致するものだけ(`query-url.js`の`parseListUrl`)。
- `getQuery()`の末尾の`limit`/`offset`は捨て、`order by`以降を並び順にする(値の中の文字列は区切りとみなさない)。
- 変換したフィールドコードの条件・並び順と元のURL(`sourceUrl`)を変更内容JSONに保存する。承認者には変換後の条件が表示される。
- 作成時の表示フィールドの初期値は、URLの`view`の一覧の表示フィールド(「（すべて）」などAPIに無い一覧なら全フィールド)。

## 使用API(kintoneドキュメントMCPで確認済み)

| API | 用途 | 必要な権限 |
| :-- | :-- | :-- |
| `GET /k/v1/apps.json` | アプリ名での検索(`name`部分一致)、アプリIDでの取得(`ids`) | 対象アプリのレコード閲覧/追加 |
| `GET /k/v1/space.json` | 対象アプリの所属スペースがゲストスペースか(`isGuest`)の判定 | スペースの閲覧 |
| `GET /k/v1/app/form/fields.json` | 対象アプリのフィールド一覧(依頼作成時・反映時の照合) | 対象アプリのレコード閲覧/追加 |
| `GET /k/v1/app/acl.json` | **対象アプリの管理権限の確認**(アプリ管理権限が無いとエラーになることを利用) | アプリ管理 |
| `GET /k/v1/preview/app/form/fields.json` | 未反映の変更の有無(運用環境との`revision`比較)、反映直前の定義取得 | アプリ管理 |
| `PUT`/`DELETE /k/v1/preview/app/form/fields.json` | 変更の反映(`revision`指定) | アプリ管理 |
| `POST`/`GET /k/v1/preview/app/deploy.json` | 運用環境への反映+完了ポーリング。失敗時は`revert: true`で取り消し | アプリ管理 |
| `GET /k/v1/record.json` | 反映直前に依頼レコードの最新の内容を取得し、画面の内容と一致するか確認 | 依頼アプリのレコード閲覧 |
| `GET`/`PUT /k/v1/preview/app/status.json` | 依頼アプリのプロセス管理の確認・ON | 依頼アプリのアプリ管理 |
| `GET /k/v1/app/views.json`、`GET /k/v1/app/status.json` | 依頼作成時の一覧の選択肢・表示フィールドの候補(プロセス管理の有無) | 対象アプリのレコード閲覧 |
| `GET`/`PUT /k/v1/preview/app/views.json` | 一覧の作成・修正・削除(全一覧を送る、`revision`指定) | アプリ管理 |
| `GET`/`POST /k/v1/preview/app/form/fields.json`、`GET`/`PUT .../layout.json` | 依頼アプリへのフィールド・スペース作成 | 依頼アプリのアプリ管理 |

- ゲストスペースのアプリはREST APIのパスが`/k/guest/{ID}/v1/...`になる。`apps.json`(ゲストスペースIDなし)は
  閲覧できるゲストスペースのアプリも返すため、`spaceId`があれば`space.json`の`isGuest`で判定し、
  ゲストスペースIDを変更内容JSONに保存する。

### 未反映の変更がある対象アプリは反映しない(実機確認済み)

デプロイAPIは「動作テスト環境のすべての設定」を運用環境へ反映するため、対象アプリで誰かが設定変更の途中
(アプリを更新していない状態)だと、その変更まで巻き込んでデプロイしてしまう。
検証環境で、未反映の変更があると`GET app/form/fields.json`(運用環境)と`GET preview/app/form/fields.json`
(動作テスト環境)の`revision`が食い違う(例: 3 と 4)こと、`revert`で一致に戻ることを確認したため、
反映前に両者を比較し、食い違う場合はエラーで中止する。

## 依頼アプリに作成するフィールド

| フィールドコード | type | ラベル | 備考 |
| :-- | :-- | :-- | :-- |
| `asr_app_id` | NUMBER | 対象アプリID | 必須。エディタが自動入力(編集不可) |
| `asr_app_name` | SINGLE_LINE_TEXT | 対象アプリ名 | 同上 |
| `asr_field_label` | SINGLE_LINE_TEXT | 対象フィールド | 「ラベル(フィールドコード)」。同上 |
| `asr_operation` | SINGLE_LINE_TEXT | 変更内容 | 変更内容の名称。同上 |
| `asr_change_json` | MULTI_LINE_TEXT | 変更内容(JSON) | 反映に使う唯一の情報源。画面では非表示 |
| `asr_reason` | MULTI_LINE_TEXT | 依頼理由 | 任意入力 |
| `asr_result` | MULTI_LINE_TEXT | 反映結果 | 完了時に自動入力 |
| `asr_applied_at` | DATETIME | 反映日時 | 完了時に自動入力 |
| (スペース)`asr_editor` | SPACER | — | 依頼の入力UI/内容表示 |

一覧画面で絞り込めるよう、アプリID・アプリ名・フィールド・変更内容は通常のフィールドにも保存するが、
反映時はJSONだけを使い、JSONのアプリIDと`asr_app_id`が一致しなければ中止する。

## 変更内容JSONの形式(`asr_change_json`)

```json
{
  "format": "kintone-app-settings-request",
  "version": 1,
  "app": { "id": "791", "name": "案件管理", "guestSpaceId": "" },
  "field": { "code": "title", "label": "件名", "type": "SINGLE_LINE_TEXT", "subtableCode": "" },
  "operation": "required",
  "before": false,
  "after": true
}
```

`before`/`after`の型は変更内容ごとに決まっている(真偽値・文字列・文字列の配列・`{min, max}`・`null`)。
反映時に`operation`のホワイトリストと値の型を厳密に検証し、不正なら何も送らない。

## プロセス管理

- 設定画面の「完了ステータス名」(既定: `完了`)へ遷移するアクションで反映を実行する。複数人の承認が必要で
  ステータスが変わらないアクション(`status`と`nextStatus`が同じ)では実行しない。
- 保存時の挙動(`GET preview/app/status.json`の結果で分岐):
  - 一度も設定していない(`states`が`null`)→ 既定フローを作成してON:
    `未申請`(作業者: 作成者)→[申請する]→`承認待ち`(作業者: 設定を保存したユーザー)→[承認する]→`完了`、
    `承認待ち`→[差し戻す]→`未申請`
  - 設定済みだがOFF → 完了ステータスがあれば既存のステータス・アクションのままONにする。無ければエラー
  - ON → 完了ステータスがあることだけ確認(無ければエラー)
- **承認経路(作業者)は必ず見直すよう設定画面に注意書きを出す。** 「承認する」を実行するユーザー
  (= 完了にするユーザー)の権限で反映APIを呼ぶため、そのユーザーが対象アプリの管理権限を持っている必要がある。
  作業者が未設定のステータスはレコードを閲覧できる全員がアクションを実行できてしまう(kintoneの仕様)。

## 反映フロー(完了アクション実行時)

0. **変更内容の確認ダイアログ**を表示する(PC: `kintone.createDialog()`に詳細画面と同じ依頼内容の表、
   モバイル: `kintone.mobile.showConfirmBottomSheet()`にテキスト)。キャンセル・閉じるでは`false`を返してアクションを
   キャンセルする(ステータスは変わらない)。ダイアログの`show()`は閉じるまで解決されないため、ローディングは確認の後に出す

1. 変更内容JSONを検証し、レコードのアプリIDと一致するか確認する
2. 依頼レコードを`GET record.json`で取り直し、画面上のJSONと一致するか確認する(承認者が古い画面で承認するのを防ぐ)
3. `GET app/acl.json`で対象アプリの管理権限を確認する(エラーなら「管理権限がありません」でキャンセル)
4. 運用環境と動作テスト環境のフィールド定義を取得し、`revision`が違えば中止(未反映の変更あり)
5. 対象フィールドが存在し、種類が依頼時と同じか確認したうえで、APIのリクエストを組み立てて送る(`revision`指定)
6. デプロイして完了をポーリング。失敗したら`revert: true`で動作テスト環境を元に戻してエラー
7. 成功したら`asr_result`・`asr_applied_at`を書き込んでアクションを続行

## モバイル

- `mobile.app.record.detail.process.proceed`でもPCと同じ反映処理を行う(モバイルでは`event.error`が使えないため、
  失敗時は`alert`して`false`を返しキャンセルする)。
- 依頼の入力UIはPCのみ。モバイルの追加/編集画面で変更内容が未入力の場合は保存時にエラーにする。

## エッジケース

- 依頼アプリ自身を対象アプリにはできない(本プラグインのフィールドを壊す操作を防ぐ)
- 対象アプリのフィールド一覧を取得できない(レコード閲覧権限なし等)→ エディタにエラー表示
- 依頼後に対象フィールドが削除・種類変更された → 反映時にエラー
- 依頼後に誰かが同じ設定を変えていた(変更前の値が現在と違う)→ 変更後の値で上書きして反映し、結果に注記する
- フィールドコード変更・削除は、そのフィールドを参照するJavaScript/プラグイン/計算式/一覧の条件に影響する旨をエディタと詳細画面で警告する

## TDD方針(`src/js/lib/`)

- `field-defs.js` — 依頼アプリに作成するフィールド定義・不足抽出・スペース追加(`plugin_config_backup`から改変)
- `api-path.js` — ゲストスペース対応のパス組み立て、APIエラーの表示文言(`plugin_config_backup`から改変)
- `deploy-poller.js` — デプロイ完了ポーリング(`plugin_config_backup`からコピー)
- `config-store.js` — プラグイン設定(完了ステータス名)の読み書き
- `target-fields.js` — 対象アプリのフィールド定義を、テーブル内も含めた選択肢の一覧に平坦化
- `option-changes.js` — 選択肢の変更(名前変更・追加・削除・並べ替え)の検証、APIのoptions組み立て、初期値の追従、表示用文言
- `operations.js` — 変更内容の定義、フィールドごとに選べる変更内容、入力値の検証、表示用文言
- `change-request.js` — 変更内容JSONの組み立て・パース・検証、反映APIのリクエスト組み立て
- `process-setup.js` — 依頼アプリのプロセス管理の設定プラン(既定フロー作成/ONにするだけ/エラー)
- `query-url.js` — 一覧画面のURLの検証(iframeで開くパスの制限)、`getQuery()`の結果の分解
- `view-changes.js` — 一覧の作成・修正・削除の検証、`views.json`に送る全一覧の組み立て、表示用文言
- `apply-runner.js` — 反映フロー全体(`api`・`wait`を注入してテスト)

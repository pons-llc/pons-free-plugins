# アプリ間突合プラグイン(cross_app_check)

## 解決したい課題

kintone標準では「アプリAには提出があるが、アプリBには提出がない人」を一覧にできない。

- 関連レコード一覧フィールドは1レコードずつ詳細画面で見るだけで、一覧化も件数集計もできない
- グラフ・クロス集計は1つのアプリの中でしか集計できない
- 結果として「妊娠届は出ているが妊娠時面談予約が出ていない妊婦を洗い出す」といった業務が、
  CSV書き出し + ExcelのVLOOKUP という手作業になっている

## 機能

集計アプリにこのプラグインを入れ、そこから基準アプリ・対象アプリを読みに行き、
突合結果をJSONファイルとして集計アプリ自身のサブテーブルに蓄積する。

```
        ┌─────────┐    ┌──────┐
        │ 妊娠届   │    │ 面談  │   ← 基準アプリ / 対象アプリ(読むだけ)
        └────▲────┘    └───▲──┘
             │             │
        ┌────┴─────────────┴────────────────────────────┐
        │ 集計アプリ(このプラグインを入れる)               │
        │  突合履歴テーブル                               │
        │   ├ 2026-08-18 10:00  対象120/未提出34  📎JSON  │
        │   └ 2026-08-11 10:00  対象118/未提出41  📎JSON  │
        │  [表示する実行 ▼] → 結果テーブルを描画           │
        └────────────────────────────────────────────────┘
```

- **母集団は基準アプリ** — 基準アプリのレコード(＋クエリ条件)が対象者一覧になる。
  対象アプリにしか存在しない人は行にならない。
- **突合キーは各アプリで1フィールドを指定し、完全一致で突き合わせる。**
  数値フィールド同士なら `1` と `01` を同一視し、文字列フィールドなら先頭ゼロを保持する
  (宛名番号のような「先頭ゼロに意味がある」コードを壊さないため)。
- **対象アプリは複数指定できる。** アプリごとに絞り込みクエリと提出日フィールドを設定できる。
- **結果はスナップショットとして追記される。** 実行のたびに履歴テーブルへ1行増え、
  過去の実行結果はドロップダウンで切り替えて表示できる(上書きしない)。
- 結果一覧は「未提出のみ表示」「対象アプリで絞る」「キー・氏名で検索」で絞り込め、
  表示中の内容をCSVでダウンロードできる。
- 突合キー・状況の各セルから、元アプリのレコードへリンクする。

## 技術アプローチ

### 集計アプリのスキーマ(プラグインが自動生成)

対象アプリを増やしてもフィールドが増えないよう、**固定スキーマ**にしている。
結果の中身はJSONファイル側が持つので、アプリ側は「実行履歴の入れ物」だけでよい。

| コード | 型 | ラベル |
| --- | --- | --- |
| `cac_title` | 文字列(1行) | 突合名 |
| `cac_runs` | テーブル | 突合履歴 |
| └ `cac_run_id` | 文字列(1行) | 実行ID |
| └ `cac_run_at` | 文字列(1行) | 実行日時 |
| └ `cac_run_summary` | 文字列(1行) | 概要 |
| └ `cac_run_file` | 添付ファイル | 結果JSON |
| `cac_view` | スペース(レイアウト要素) | 結果表示領域 |

設定画面の「集計用フィールドを作成」ボタンが、不足しているものだけを追加してデプロイする
(冪等。既存フィールドには触らない)。スペースはフィールド追加APIでは作れないため、
レイアウト変更API(`PUT /k/v1/preview/app/form/layout.json`)で差し込んでいる
(`scripts/kintone-admin.js`の`ensureSpacerInLayout`と同じ手順をブラウザ側に実装し直したもの)。

### レコードの取得

別アプリのレコード取得にJavaScript APIは存在しないため、`kintone.api()`(内部向けラッパー)で
REST APIを呼ぶ。全件取得には**カーソルAPIを使わず、`$id`昇順ページング**を使っている。
カーソルは「1ドメインで同時に10本まで・作成は排他」という制約があり、共有環境では
他のカスタマイズと取り合いになって詰まるため。

### ファイルの読み書き

ファイルのアップロード/ダウンロードAPIは、kintone公式ドキュメントで明示的に
`kintone.api()`が非対応と記載されている。そのため`js/file-client.js`の2箇所だけ、
同一オリジン(kintone自身)への`fetch`を直接使う。外部ドメインへの通信は一切行わない。
POSTにはCSRFトークン(`__REQUEST_TOKEN__`)が必要。

### サブテーブルの更新

レコード更新APIでサブテーブルを更新するときは**既存の全行をリクエストに含める**必要がある
(含めなかった行は削除される)。行の`id`と、既存行に添付済みのファイルの`fileKey`も
そのまま持ち越さないと、過去の結果ファイルが消えてしまう。
`js/lib/run-history.js`の`carryOverRow`がこれを担当している。

履歴は既定20件で頭打ちにし、超えた分は古い行から落とす
(kintone公式が「1つのテーブルに大量の行を追加しないでください」と明記しているため)。

### 結果JSONの形

```json
{
  "schemaVersion": 1,
  "runId": "20260818-100000-ab12",
  "runAt": "2026-08-18T01:00:00Z",
  "labels": { "submitted": "提出済", "unsubmitted": "未提出" },
  "baseApp": { "appId": "570", "name": "妊娠届", "query": "", "keyFieldCode": "宛名番号" },
  "targets": [{ "appId": "571", "label": "面談", "query": "", "dateFieldCode": "面談日" }],
  "summary": {
    "baseCount": 4, "skippedNoKey": 0, "unsubmittedAny": 2,
    "perTarget": [{ "label": "面談", "submitted": 2, "unsubmitted": 2 }]
  },
  "rows": [
    { "key": "A-001", "name": "山田花子", "baseRecordIds": ["1"],
      "targets": [{ "submitted": true, "count": 2, "lastDate": "2026-07-20", "recordIds": ["1","2"] }] }
  ]
}
```

## 設定画面

1. **集計用フィールド** — 「集計用フィールドを作成」ボタン(上記スキーマを生成)
2. **基準アプリ** — アプリID → フィールド読込 → 突合キー / 表示名 / 絞り込みクエリ
3. **対象アプリ**(「+ 対象アプリを追加」で増やせる) — アプリID・突合キー・提出日・表示ラベル・クエリ
4. **表示と上限** — 提出済/未提出の表記、1アプリあたりの読み込み上限、保持する履歴件数

基準アプリ・対象アプリは別アプリなので`kintone.app.getFormFields()`が使えず、
`GET /k/v1/app/form/fields.json`で取得している(集計アプリ自身はJavaScript APIを使う)。

## 画面ごとの挙動

- **レコード詳細画面** — ヘッダーに「突合を実行」ボタン、`cac_view`スペースに結果ビューワ。
  1レコードが1つの突合結果の入れ物になる。
- 設定が未完了、または集計用フィールドが未作成のときは、その旨を画面に出す。
- モバイルには対応していない(結果テーブルの表示に画面幅が要るため)。

| `app-schema.js` | 集計アプリの固定スキーマと差分抽出 |

| `row-filter.js` | ビューワの絞り込み |
| `csv.js` | CSV出力 |
| `run-id.js` | 実行ID・実行日時 |

実環境E2E(`src/e2e/full-flow.e2e.test.js`)では、単体テストでは分からない次の点を確認している。

- **サブテーブルの中に添付ファイルフィールドをAPIで作成できること**(このプラグインの前提)
- スペースがレイアウトに入り、`getSpaceElement()`で取れること
- 突合実行 → JSON添付 → 履歴1行増加、未提出者が画面に出ること
- 2回実行しても上書きされず履歴が2行になること
- ドロップダウンで過去の実行に切り替えられること

E2Eは共有の`TEST_APP_ID_1/2`ではなく、このプラグイン専用の3アプリを使う
(レコードを毎回作り直すため。詳細は`src/e2e/fixtures.js`のコメント参照)。

## 未解決・利用時の注意点

- **突合キーは単一フィールドの完全一致のみ。** 「氏名＋生年月日」のような複合キーや、
  表記ゆれ(全角/半角、旧字体)の吸収はしていない。共通のID項目を持たない運用では使えない。
- **突合結果には個人情報(氏名・キー)がJSONファイルとして残る。**
  集計アプリのアクセス権を、閲覧してよい担当者だけに絞ること。
- **実行は手動のみ。** kintoneプラグインから定期実行はできないため、
  「毎月1日に実行する」といった運用は人が行う必要がある。
- 実行直後、結果ビューワは即座に更新されるが、レコード上の「突合履歴」テーブルは
  kintoneが最初に描いたままなので、画面を再読み込みするまで新しい行が現れない
  (その旨を画面のメッセージで案内している)。
- 1アプリあたりの読み込み上限(既定5000件)を超えると、超過分は突合されない。
  超えた場合は画面に警告を出す。
- 画面に一度に描くのは500行まで。それを超える場合はCSVでダウンロードする。
- API実行数は「(基準アプリの件数 ÷ 500) + Σ(対象アプリの件数 ÷ 500) + 3」程度。
  対象者が数千人規模になると1回の実行で十数回のAPIを消費する。

# 削除バックアッププラグイン

## 機能概要

レコード詳細画面・レコード一覧画面でのレコード削除の直前(`app.record.detail.delete.submit`/
`app.record.index.delete.submit`、いずれもPC。削除をキャンセルできる「保存前」イベント)に発火し、
削除されるレコードの内容(添付ファイルを含む)を必ずバックアップしてから削除を許可する。
バックアップ方式はプラグイン設定で以下のどちらか1つを選ぶ(設定は1系統のみ、行の複数追加はしない)。

- **zip方式**: レコードのJSON情報と添付ファイルをまとめたzipファイルをブラウザからダウンロードする。
- **アーカイブ方式**: 指定した別アプリに1レコードを新規登録し、レコードJSON情報を指定の文字列
  フィールドへ、添付ファイルを指定の添付ファイルフィールドへ保存する。

**バックアップに失敗した場合は削除そのものをキャンセルする**(`event.error`を設定して`event`を返す)。
「削除はできたがバックアップは失敗した」という状態を作らないことを最優先する。

## 対応イベント・対応画面(確定)

- `app.record.detail.delete.submit`(レコード詳細画面)
- `app.record.index.delete.submit`(レコード一覧画面)

**PCのみ対応。モバイルは対象外**とする。理由: `app.record.index.delete.submit`はkintone公式ドキュメント
上もモバイル版イベントが存在しない(一覧からの個別削除にモバイルの削除操作自体が無い)。詳細画面の削除は
モバイル版イベント(`mobile.app.record.detail.delete.submit`)が存在するが、「一覧・詳細どちらから消しても
同じバックアップが必ず効く」という一貫性を優先し、今回はPC限定にスコープを絞った。

両イベントのイベントオブジェクトは`type`/`appId`/`recordId`/`record`のみで同じ形(kintoneドキュメント
MCPで実際に確認済み、`record`はREST APIの「フィールド形式」と同じオブジェクト)。一覧画面での一括削除も、
レコード1件ごとにこのイベントが個別に発火する(`records`のような複数形プロパティは無い)ため、
1レコード単位の処理だけを実装すればよい。

## 添付ファイルの扱いに関する重要な制約(kintoneドキュメントMCPで確認済み・設計上の確定事項)

削除されるレコードから`event.record`経由で取得できる添付ファイルの`fileKey`(例:
`201202061155587E339F9067544F1A92C743460E3D12B3297`という長いハッシュ形式)は、
[フィールド形式](https://cybozu.dev/ja/kintone/docs/overview/field-types/)・
[ファイルをアップロードするAPI](https://cybozu.dev/ja/kintone/docs/rest-api/files/upload-file/)の両方に
明記されている通り**「ファイルダウンロードにのみ利用できる」**。レコード登録APIの添付ファイル
フィールドへ指定できる`fileKey`は、[ファイルをアップロードするAPI](https://cybozu.dev/ja/kintone/docs/rest-api/files/upload-file/)
のレスポンスで得られるUUID形式の一時fileKeyのみであり、**レコード取得由来のfileKeyをそのまま
アーカイブ先レコードに貼り付けることはkintoneの仕様上不可能**(当初の想定「ファイルの再アップロード
ではなくファイルキーのコピー」は技術的に実現できないことをユーザーに確認・合意済み)。

このため、アーカイブ方式・zip方式のどちらも実際には次の流れで処理する。

1. `GET /k/v1/file.json?fileKey=...`(fetch。この2API(ファイルアップロード/ダウンロード)は
   `kintone.api()`が明示的に非対応と公式ドキュメントに明記されているため、同一オリジン
   (kintone自身)へのfetchのみを使う。外部ドメインへの送信は一切行わない)でファイル本体を取得する。
2. アーカイブ方式の場合のみ、取得したBlobを`POST /k/v1/file.json`(multipart/form-data、fetch、
   `kintone.getRequestToken()`をCSRFトークンとして付与)で一時保管領域へ**再アップロード**し、
   新しい一時fileKeyを得る。ユーザー操作としての「手動再アップロード」は発生しない
   (プラグインが自動で行う)が、API呼び出しとしてはダウンロード1回+アップロード1回が
   添付ファイル1つにつき必ず発生する。
3. zip方式の場合はダウンロードしたBlobをそのままzipへ格納する(再アップロードは不要)。

## zip方式の詳細(確定)

- 外部ライブラリを使わない方針(CLAUDE.md開発方針9)のため、ZIPファイル生成をvanilla JSで自前実装する
  (`js/lib/build-zip.js`)。圧縮アルゴリズム(DEFLATE)は実装せず、**格納(STORE、無圧縮)方式のみ**
  対応する(十分小規模なバックアップ用途であり、複雑なDEFLATE実装を避けて正確性を優先)。
  CRC-32は標準的なテーブル方式で自前実装する(`js/lib/crc32.js`)。
- zipの内容:
  - `record.json` — `{ appId, recordId, deletedAt(ISO8601), record }`(`record`はイベントオブジェクトの
    生の値をそのまま)をJSON.stringifyしたテキスト
  - `files/<フィールドコード>/<元のファイル名>` — レコード内の全FILEタイプフィールドの全ファイル
    (フィールドが複数あっても1つのzipにまとめる)。同一フィールド内でファイル名が重複した場合は
    `name (2).ext`のように連番を付けて衝突を回避する(`js/lib/build-zip-entry-names.js`)。
- ファイル名: `backup_app{appId}_record{recordId}.zip`
- ダウンロードは`Blob`+`<a download>`要素のクリックで行う(外部通信なし)。

## アーカイブ方式の詳細(確定)

設定でアーカイブ先の情報を指定する。

- **アーカイブ先アプリID**(数値)
- **JSON保存先フィールド**(アーカイブ先アプリの文字列(1行)または文字列(複数行)フィールドから選択。
  レコード全体のJSONを保存するため、文字数制限に余裕のある**文字列(複数行)を推奨**する
  (設定画面・security-checklistに明記する。文字列(1行)を選んで文字数上限を超えた場合は
  レコード登録APIがエラーを返し、その他の失敗と同様に削除がキャンセルされる)。
- **添付ファイル保存先フィールド**(アーカイブ先アプリの添付ファイルフィールドから選択。元レコードの
  全FILEフィールドの全ファイルをこの1フィールドにまとめて保存する)

アーカイブ先アプリはプラグインが動作しているアプリと異なる(別アプリ)ため、
`kintone.app.getFormFields()`は使えない(現在開いているアプリにしか使えないJavaScript API)。
設定画面で「フィールドを取得」ボタンを押すと、`kintone.api(kintone.api.url('/k/v1/app/form/fields.json',
true), 'GET', { app: archiveAppId })`(REST API、kintone自身への呼び出しのみなので
`kintone.api()`を使用)でアーカイブ先アプリのフィールド一覧を取得し、型でフィルタした2つの
プルダウンを描画する(CLAUDE.md開発方針3)。

登録は`kintone.api(kintone.api.url('/k/v1/record.json', true), 'POST', { app, record })`
(1件登録API)を使う。

## 設定画面(確定)

行の複数追加はせず、1系統のみの設定。

- バックアップ方式(ラジオボタン): 「zipでダウンロード」/「別アプリへアーカイブ」
- (アーカイブ方式のときのみ表示)
  - アーカイブ先アプリID(数値入力)
  - 「フィールドを取得」ボタン
  - JSON保存先フィールド(プルダウン、取得後に選択可能になる)
  - 添付ファイル保存先フィールド(プルダウン、取得後に選択可能になる)

保存時のバリデーション(`js/lib/config-validation.js`):

- バックアップ方式が`zip`/`archive`のいずれかであること
- `archive`の場合: アーカイブ先アプリIDが1以上の整数であること、JSON保存先・添付ファイル保存先の
  両方が選択されていること、かつ両者が異なるフィールドであること

## アーカイブ先アプリの必須フィールドに関する制約(実機で確認済み)

アーカイブ先アプリに、JSON保存先・添付ファイル保存先以外の必須フィールドが存在すると、レコード登録
(`POST /k/v1/record.json`)が必ず400エラーになり、その結果「バックアップ失敗→削除キャンセル」の
フェイルセーフが働いて**削除自体が常にできなくなる**。E2Eテスト実装時に実際に踏んだ不具合
(共有の検証アプリ`TEST_APP_ID_2`に存在する既存の必須・重複禁止フィールド「文字列__1行_」が
未入力のままだったため`CB_VA01`エラーになった)であり、机上の想定ではなく実機で確認した制約。
設定画面・security-checklist.mdに「アーカイブ先はこのプラグイン専用の空アプリ、または他に
必須フィールドの無いアプリを推奨する」旨を明記した。

## エッジケース(確定)

- 添付ファイルが1つも無いレコード: zip方式は`record.json`のみのzipを作る。アーカイブ方式は
  添付ファイル保存先フィールドの値を空配列`[]`で登録する。
- ファイルのダウンロード・再アップロード・レコード登録のいずれかに失敗した場合:
  `event.error`にエラー内容を設定して削除をキャンセルする(データを失わないことを最優先)。
- バックアップ処理中は`kintone.showLoading('VISIBLE')`/`kintone.showLoading('HIDDEN')`
  (`kintone.app.showLoadingModal()`ではなくこちらが正しいAPI名、kintoneドキュメントMCPで確認済み)
  で操作をブロックし、二重クリックを防ぐ。
- レコード一覧からの一括削除は1レコードずつイベントが発火するため、複数レコードを連続削除すると
  アーカイブ方式ではアーカイブ先アプリに複数レコードが逐次登録される(まとめて1レコードにはしない)。

## TDD(`src/js/lib/`のみJestでユニットテスト、`pnpm test`)

- `crc32.js` — 標準チェック値(`"123456789"` → `0xCBF43926`)で検証
- `build-zip.js` — 生成したバイト列を自前でパースし、シグネチャ・ファイル名・CRC・サイズ・
  エントリ数(EOCD)が正しいことを検証(0件・複数件・日本語ファイル名を含むケース)
- `collect-file-fields.js` — レコードオブジェクトからFILEタイプの全フィールドの全ファイルを
  フィールドコード付きで抽出する(複数FILEフィールド・フィールド内複数ファイル・FILEフィールド
  無しのケース)
- `build-zip-entry-names.js` — フィールドコード別ディレクトリへの割り当てとファイル名衝突時の
  連番衝突回避
- `backup-payload.js` — バックアップ用JSON文字列の組み立て(JSON.parseでの往復一致を確認)
- `config-store.js` — 設定の読み込み/初期値/保存
- `config-validation.js` — 設定のバリデーション(上記ルール)

kintone依存のグルーコード(`desktop.js`/`config.js`、fetch・`kintone.api()`呼び出しを含む)は
`src/e2e/*.e2e.test.js`(Puppeteer、`pnpm run test:e2e`)で実環境テストする。

## 実機テスト方針

- `TEST_APP_ID_1`を削除対象アプリとする。添付ファイルフィールドが元々無いため、テスト専用の
  `dback_test_file`(FILE)を`ensureFormFields()`で冪等に用意する。
- アーカイブ先には`TEST_APP_ID_2`を使わず、このプラグイン専用の新規アプリ(`fixtures.js`の
  `DBACK_ARCHIVE_APP_ID`、実際に作成したアプリID: 600)を使う。`TEST_APP_ID_2`には既存の
  必須・重複禁止フィールド「文字列__1行_」があり、上記の「アーカイブ先アプリの必須フィールドに
  関する制約」により登録が必ず失敗するため(`fiscal_year_numbering`が専用のカウンターアプリを
  作成しているのと同じ考え方)。
- 設定画面のE2Eでは、モード切り替えでアーカイブ設定欄の表示/非表示が切り替わること、
  「フィールドを取得」ボタンでプルダウンの選択肢が実際に絞り込まれること(添付ファイル
  フィールドのみ/文字列フィールドのみ)を確認する。
- 削除フローのE2Eでは、レコードを1件作成→詳細画面で削除→(zip方式)ダウンロードが発生すること、
  または(アーカイブ方式)アーカイブ先アプリにレコードが1件増え、JSON・添付ファイルが保存されて
  いることをREST API経由で確認する(`scripts/kintone-admin.js`の`request()`を使う)。
